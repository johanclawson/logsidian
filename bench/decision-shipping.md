# Decision memo: what to offer the launcher now (Fable arbiter, 2026-09-12)

## 1. Decision: offer (b), a perf-only build, and hold RC3

**Not RC3, not nothing.** RC3 passes the harness, but two Codex HIGH sets stand, one of them (guard finding 1) is an ordering that RC3 *creates*: block identity keeps the uuid, the save fix lets the stale repair land, the guard sees base E and stamps `written`. On master that same repair fails with INode and external text survives. RC3 also has an open, unexplained UI regression confined to the save path (typing-window UI long tasks RC2 -> RC3: real 5/578 ms -> 35/5957 ms; save median 88 -> 136 ms). Nothing that touches the write path or the editor goes to the system of record with an open regression and an open HIGH.

**(b) is no worse than master on the write path, by construction and by measurement.** The perf commits touch no write-path file: `fs/node.cljs`, `electron/handler.cljs`, `worker/file.cljs` are untouched, and the only `watcher_handler.cljs` hunk (c3bbfd6) swaps `<get-files` for `<get-file-paths`, same set. The reconcile is master's. The step-4 build, which is (b) minus the automerge fix, the node LRU and two boot follow-ups, passed 5/8 harness scenarios against master's 3/8; the three shared failures (config-offline, two-ops-one-flush, external-rewrite overwrite) and the INode save failure are master's own. The two extra passes are search finding offline edits (per-tx indexing, a real change) and burst-writes, which no write-path change explains, so count it as "not worse", not "better". Honest framing for Johan: (b) fixes none of master's four data-loss orderings; it changes what he waits for, not what he can lose.

**Contents of (b): branch at `046febb`** (the last commit before the first reconcile commit `0fc9d20`), plus a cherry-pick of `995fe78` (test-only, stops the repo-test leak). Code commits, in order: b7ad11c instrumentation, f180a95 journals paging, c3bbfd6 file-paths index, f81f43e linked-refs index walk, 9cd26a2 sliced worker search index, 9ba71ff NOW fast path, 3266c70 FTS rowid fix + schema version, 25caa27 save timing, 5272790 / 8458285 / 7ff9b2b / 66c71d7 step-4 write path and tick, c1b8bec / 04df66e / 5d0fd2e / da86851 boot fixes, c29621c automerge fix, 06c5e86 / c8a73ea boot follow-ups, d45c828 / fc589da / 046febb restored-node LRU. Bench-only commits in the range are harmless.

**Excluded, deliberately: the promesa patch (32f102e).** The plan of record listed it in the perf batch, but nothing in (b) needs it (the "p/catch did not catch" symptom was in the reconcile's `<map-bounded`, which (b) does not contain), master has run on the buggy drain loop all along, and it is one of the three suspects for the typing regression. Re-admit it after the UI profile names the cause and a (b)+promesa run shows typing-window UI tasks at RC2 level. Same logic keeps identity and the save fixes out.

**(b) has not been built and gated as itself.** Before it is offered: build it, full suite (expect 437/2876, only get-class-objects-test), all 8 harness scenarios (expect 5/8 with master's three failures, and that no scenario master passes fails), release gate on the real-graph copy (0/569 changed, 0 new bak), and one lsbench `real` reopen + typing run showing UI typing tasks at RC2 level (~5 tasks / ~0.6 s) and the LRU's memory cost against the 4 GB floor.

## 2. Fix plan before guard, save fixes and identity ship (RC4)

Order by "regression vs master" first, then new mechanisms with holes, then inherited gaps. One branch, one re-review.

0. **Name the typing regression** (profile in progress). Gates everything below, because it decides whether identity or promesa change shape.
1. **G1, must fix.** Automatic id repairs carry `{uuid property value}`; the worker builds the title from its *current* block. No renderer-built full title may be an automatic last writer. Tests: worker unit test where the entity's title changed after the op was built -> result is current title + `id::`; harness `idrepair-vs-external-edit`: reopen a graph with id-less referenced blocks, rewrite the page externally during the reconcile; fail unless disk == E plus `id::` lines and no LSGUARD `written` carries old text.
2. **S1 + S2, must fix.** Insert targets resolved by uuid inside the worker tx (rescued targets included), paste placement recomputed after rescue, editor buffer retained until every constituent op succeeds; last-sent advances on ack, identical pending saves return the pending promise, failures keep the text retryable. Tests: outliner core-test insert with stale id + valid uuid; editor-test rejecting worker -> second save of T is sent, blur awaits a pending rescue; harness `enter-split-after-reparse`: type, external rewrite of the same page, Enter mid-text, type, close; both halves on disk or in a conflict copy.
3. **G3, must fix (minimal).** Reopen never deletes a page or backs up a mismatched stamp through ordinary retention: copy the DB content into the conflict tree and notify first. Persisting pending status can wait. Tests: reconcile unit test (absent file -> conflict copy before deletion); harness `crash-between-stamp-and-write`: SIGKILL right after typing into a new page and into an existing page, reopen; text in `logseq/bak/conflicts/`, existing page's disk == E.
4. **G2 and G4, must fix (small).** Route mkdir/preparation failures through `<handle-failed-write!` (copy, notice, LSGUARD, `*failed-writes`); a failed snapshot copy is tracked and the notice says which edits are lost. 5. **Same series, not gating:** G5 (stamp ownership by request id), G6 (`writable?` returns true; one line), G8 (`unlinkSync`), S3 (carry repo + page uuid with the edit), S6 (deletion provenance), S7 (full text to a conflict file, explicit failed result).

Acceptance for RC4: unit tests above, 8 + 3 harness scenarios green with the guard present, gate 0/569, typing-window UI tasks at RC2 level, the pending identity reviews (Fable, Codex after 20:45) closed, then **one high-effort Codex re-review of the whole guard + save + identity range** as a unit, because the findings are interactions. ## 3. Evidence package for Johan, and rollback

**Numbers (b) delivers** (RC2 measurements for the same code, minus reconcile and guard): longest boot task 5.6 s -> 2.6 s (mean of three); journals list 102 ms -> under 50 ms and paged; first search "möte" on his graph 1.75 s -> ~1.2 s; restored index nodes after a GC 729 -> 0, a repeated 10k search 480 -> 375 ms; search rebuild at 10k 254 s -> 180 s with no slice over 0.8 s (step 4 alone had 5.4 s stalls; the automerge fix removed them); worker time per save median 94 ms at 10k; peak memory at reopen 1.16 GB. One visible behaviour change: search finds edits made while the app was closed or by Jarvis (master's index misses them).

**Safety results**: full suite 437/2876 (one known upstream error); harness 5/8 with master's three failures and none new; gate: reopening a copy of his graph changed 0 of 569 files, no backup. **Not fixed by (b)**: offline edits invisible to search is fixed, but burst saves, stale proposals overwriting an external rewrite, config rewrite after a deleted home page, and the INode typing loss remain exactly master's.

**Residual risks**: the restored-node LRU is the one perf commit on the data path (a stale node after a store would serialize wrong content); it is invalidated on store, unit-tested, and the gate passed with it twice, so its canary is the soak. Per-transaction search indexing adds first-open cost (measured, bounded). The packaged worker carries LSPERF console lines (benign). The RC3 typing regression is why the write-path work is held.

**Soak and canaries**: Johan uses it daily for a week with Jarvis appending. `lsgit diff` / `lsgit log` (history in `~/.logseq-history`, outside OneDrive) hourly; any new file under `logseq/bak/`; INode errors in the console. One unexplained bak file or diff reverts.

**Rollback**: `~/.local/bin/logsidian` hard-codes `APP_DIR=~/dev/logsidian/static/out/Logseq-linux-x64` (the master build). Build (b) into a separate directory and have the launcher read `APP_DIR` from `$LOGSIDIAN_APP_DIR` or a `current` symlink; rollback is repointing it, no rebuild, master's build stays on disk. Graph files are untouched by either build. The search db carries a schema version (3266c70); if master's search misbehaves after a rollback, "Rebuild search index" from the UI restores it. Recovery of any file: `lsgit restore <file>`, then `logseq/bak/`, then OneDrive version history.
